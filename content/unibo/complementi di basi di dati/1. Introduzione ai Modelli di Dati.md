# Introduzione ai Modelli di Dati: Strutturati, Semi-strutturati e Non strutturati

**Tags:** #data_management #database #xml #information_retrieval #unibo
**Argomento:** Classificazione strutturale dei dati e limiti del modello relazionale.

---

## 1. Introduzione e Contesto
Tradizionalmente, i sistemi di gestione dei dati relazionali ([[RDBMS]]) sono stati pilastri fondamentali per applicazioni critiche come i sistemi bancari e le grandi aziende. Tuttavia, il panorama digitale odierno è cambiato drasticamente: la maggior parte dei dati disponibili oggi **non è in forma relazionale**.

La diffusione di Internet e delle piattaforme di media sharing ha intensificato la produzione di enormi quantità di dati con proprietà diverse rispetto a quelli gestiti dai sistemi relazionali classici.

---

## 2. Classificazione Strutturale dei Dati

Possiamo classificare i dati lungo uno spettro basato sulla rigidità della loro struttura:

### A. Dati Strutturati (Structured Data)
Sono i dati classici gestiti dai database relazionali.
* **Caratteristiche:** Esiste una chiara distinzione tra **schema** (la struttura) e **dati** (il contenuto).
* **Esempio:** Una tabella con colonne predefinite come `id-pers`, `nome`, `cognome`. Ogni riga deve rispettare questa struttura rigida.

### B. Dati Non Strutturati (Unstructured Data)
Si trovano all'estremo opposto dello spettro. Sono spesso chiamati "Raw Data" (dati grezzi).
* **Caratteristiche:** Non seguono uno schema predefinito o riconoscibile dal sistema in modo nativo.
* **Esempio:** File di testo narrativo, immagini (bitmap), video, audio.
* **Gestione:** Richiedono elaborazioni specifiche; l'area di ricerca che si occupa di gestire e accedere a questi dati è l'[[Information Retrieval]].

### C. Dati Semi-strutturati (Semi-structured Data)
Si collocano nel mezzo. Possiedono proprietà ibride tra i dati strutturati e quelli non strutturati.
* **Caratteristiche:** Hanno una struttura parziale o irregolare. Spesso lo schema è mescolato ai dati stessi ("self-describing").
* **Esempio:** Documenti [[XML]], pagine [[HTML]], JSON. Qui i tag (come `<title>`, `<body>`) forniscono una struttura, ma il contenuto interno può essere libero o misto.

---

## 3. Confronto: Dati Relazionali vs Semi-strutturati

Esistono differenze fondamentali nel modo in cui queste due tipologie organizzano l'informazione:

| Caratteristica | Dati Relazionali | Dati Semi-strutturati |
| :--- | :--- | :--- |
| **Schema** | Distinzione netta tra schema e dati | Schema parziale con le stesse proprietà dei dati |
| **Concetto base** | Basati sul concetto di **Insieme** (Set) | Basati sul concetto di **Lista** (List) o Albero |
| **Ordinamento** | Non ordinati (l'ordine delle righe non conta) | Ordinati (l'ordine degli elementi è significativo) |
| **Nidificazione** | Non annidati (struttura piatta) | Annidati (struttura gerarchica/nested) |

## 4. XML e la Rappresentazione dei Dati

L'[[XML]] (eXtensible Markup Language) è il formato principale per la rappresentazione dei dati semi-strutturati. Viene utilizzato per:
1.  **Scambio dati:** Rappresentare dati strutturati per scambiarli tra applicazioni diverse (es. export da un DB relazionale a XML).
2.  **Rappresentazione nativa:** Rappresentare dati intrinsecamente semi-strutturati, sfruttando la flessibilità di indicare sia il dato che lo schema.

### Il problema di adattare l'XML al Modello Relazionale
Quando si tenta di forzare dati gerarchici (come un albero XML di progetti e referenti) in tabelle relazionali piatte, sorgono problemi significativi:
* **Perdita di semantica:** La struttura ad albero visibile e leggibile in XML si perde, frammentandosi in tabelle di relazioni "genitore-figlio" difficili da leggere per un umano.
* **Complessità delle query:** Domande apparentemente semplici (es. *"Trova tutti i referenti che partecipano al secondo progetto"*) diventano complesse in SQL. Richiedono ricorsione o join inefficienti, aumentando i tempi di accesso.
* **Trend attuale:** Invece di adattare il relazionale, la tendenza è sviluppare sistemi specifici per XML o NoSQL.

## 5. Limiti del Modello Relazionale (Esempio del Libro)

Consideriamo la rappresentazione di un libro ("L'arte della guerra" di Sun Tzu).
In un modello relazionale avremmo una tabella con: `Autore`, `Titolo`, `Nascita`, `Testo`.

**Criticità:**
1.  **Rigidità strutturale:** Se volessimo aggiungere informazioni eterogenee (es. "Data di morte" per un autore o una "Descrizione" aggiuntiva), dovremmo modificare la struttura dell'intera tabella (DDL), il che è costoso e inefficiente se l'attributo serve solo per pochi record.
2.  **Scambio dati:** Per scambiare questi dati con un'altra applicazione, non basta inviare i dati; bisogna inviare anche la struttura (lo schema), altrimenti i dati sarebbero incomprensibili.
3.  **Campi testuali:** Il campo `Testo` conterrebbe migliaia di caratteri senza alcuna struttura interna interrogabile via SQL standard.

## 6. Proprietà dei Dati Semi-strutturati

I dati semi-strutturati (come il Web o XML) mostrano proprietà uniche:
1.  **Struttura irregolare o parziale:** I documenti possono avere campi mancanti o aggiuntivi (es. un'immagine all'interno di un testo).
2.  **Schema "a posteriori" (Data Guide):** Spesso non si definisce lo schema prima di inserire i dati. Lo schema viene dedotto dai dati stessi (data-driven).
3.  **Schema molto ampio:** Pensiamo al Web come a un enorme database; lo "schema" copre domini infiniti (trasporti, governo, università).
4.  **Evoluzione rapida:** Lo schema cambia frequentemente (es. link che si rompono, siti che cambiano struttura), rendendo impossibili gli aggiornamenti rigidi tipici dei DB relazionali.

## 7. Dati Non Strutturati e Information Retrieval

Quando lo schema è assente o non utilizzato (es. testo libero, multimedialità), entriamo nel dominio dell'[[Information Retrieval]] (IR). Esempi classici sono i motori di ricerca web.

### Differenze nelle Query (Interrogazioni)
* **DBMS Relazionale:** Usa linguaggi complessi (SQL) per requisiti precisi.
    * *Esempio:* `SELECT nome FROM persone WHERE età > 40`.
    * *Modello:* **Booleano**. Una tupla fa parte del risultato O non ne fa parte (Vero/Falso). Richiede correttezza e completezza.
* **Information Retrieval:** Usa query semplici, spesso liste di parole chiave.
    * *Esempio:* `Return documents containing "battle"`.
    * *Modello:* **Ranking** (Classifica). Data l'ambiguità del linguaggio naturale, non si può dire con certezza se un documento è rilevante. I risultati sono ordinati per **grado di rilevanza** (relevance score). L'utente accetta un certo margine di errore o "rumore".

### Confronto Finale: Relazionale vs Non Strutturato

| Relazionale | Non Strutturato (IR) |
| :--- | :--- |
| Distinzione chiara Schema/Dati | Nessuno schema (o non usato) |
| Query Language (Linguaggio di interrogazione) | Search Language (Linguaggio di ricerca) |
| Modello Booleano (Esatto) | Modello a Ranking (Probabilistico/Rilevanza) |
| Aggiornamenti parziali | Aggiornamenti totali (spesso si re-indicizza) |

**Nota:** I moderni DBMS stanno integrando capacità di IR, ad esempio tramite l'indicizzazione di colonne testuali (CLOB) o dati multimediali (BLOB), cercando di colmare il divario tra i due mondi.
