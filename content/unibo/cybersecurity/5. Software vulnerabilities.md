## 1. La Realtà dello Sviluppo Software
Il software è l'unico prodotto industriale che viene rilasciato con difetti noti e accettati. A differenza di un'automobile o di un ponte, dove un difetto di progettazione comporta richiami massivi e responsabilità legale, nel mondo software vige la prassi del "rilascia ora, correggi dopo" (patching).

### La Densità dei Difetti
La complessità del software moderno rende statisticamente impossibile l'assenza di errori.
* **Statistiche:** Si stima che ci siano tra **0.5 e 5 difetti per ogni 1000 righe di codice (LoC)**.
* **Impatto:** Considerando che sistemi operativi come Windows o Linux hanno decine di milioni di righe di codice, il numero di bug latenti è nell'ordine delle migliaia.
* **90/10 Rule:** Almeno il 90% delle vulnerabilità di sicurezza deriva da errori software (bug di implementazione o difetti di design).

## 2. Le Vulnerabilità di Memoria (Memory Corruption)
Queste vulnerabilità derivano dalla gestione insicura della memoria, tipica di linguaggi come C e C++ che non impongono controlli automatici sui limiti dei buffer.

### Buffer Overflow
È la vulnerabilità "regina" degli ultimi decenni. Si verifica quando un programma scrive più dati in un buffer (area di memoria) di quanti ne possa contenere, sovrascrivendo le aree di memoria adiacenti.

* **Meccanismo (Stack Smashing):** Nello *Stack* di memoria, le variabili locali, i puntatori e l'indirizzo di ritorno (Return Address - EIP/RIP) sono salvati in sequenza.
* **L'Attacco:** Se un attaccante riesce a scrivere oltre il buffer assegnato per una variabile (es. un campo input troppo lungo non controllato), può sovrascrivere il **Return Address**.
* **L'Obiettivo:** Sostituire l'indirizzo di ritorno legittimo con l'indirizzo di un codice malevolo inserito dall'attaccante (spesso chiamato **Shellcode**). Quando la funzione termina, il processore salta all'indirizzo malevolo ed esegue il codice dell'attaccante (spesso aprendo una shell di comando remota).
* **Contromisure:** ASLR (Address Space Layout Randomization), Stack Canaries (valori sentinella che rilevano la sovrascrittura), DEP (Data Execution Prevention).

### Integer Overflow
Accade quando un'operazione aritmetica produce un risultato che supera il valore massimo rappresentabile dal tipo di variabile (es. un intero a 8 bit che supera 255 diventa 0). Questo può portare a comportamenti imprevisti, come l'allocazione di buffer troppo piccoli che poi causano un Buffer Overflow.

## 3. Vulnerabilità Web e Input Validation
La regola d'oro della sicurezza software è: **"All Input is Evil"** (Tutto l'input è malevolo). Mai fidarsi dei dati provenienti dall'utente senza validazione e sanitizzazione.

### SQL Injection (SQLi)
Si verifica quando l'input dell'utente viene concatenato direttamente in una query SQL senza validazione. L'attaccante può inserire comandi SQL che il database esegue.
* **Esempio Classico:** Inserire `' OR '1'='1` in un campo login. Poiché 1=1 è sempre vero, la condizione diventa vera per tutti i record, permettendo l'accesso senza password (bypass dell'autenticazione).
* **Impatto:** Furto di dati, cancellazione di tabelle, modifica dei dati.
* **Soluzione:** Usare **Prepared Statements** (o query parametrizzate) che separano il codice dai dati.

### Cross-Site Scripting (XSS)
L'attaccante inietta script malevoli (solitamente JavaScript) in pagine web visualizzate da altri utenti. Il browser della vittima esegue lo script credendo che provenga dal sito fidato.
* **Reflected XSS:** Lo script malevolo è contenuto in un link (es. parametri URL). Quando la vittima clicca, il sito "riflette" l'input nel browser, eseguendo lo script.
* **Stored XSS:** Lo script viene salvato permanentemente sul database del server (es. in un commento o post di un forum). Chiunque visualizzi quella pagina eseguirà lo script.
* **Obiettivo:** Furto di cookie di sessione (Session Hijacking), redirect verso siti di phishing.

### Cross-Site Request Forgery (CSRF)
L'attaccante induce la vittima (già autenticata su un sito) a compiere un'azione indesiderata a sua insaputa (es. cambiare la password o fare un bonifico) semplicemente visitando una pagina trappola.

## 4. Controllo Accessi e Autenticazione
Errori nella gestione delle identità e dei permessi.

### Broken Authentication
Include vulnerabilità come:
* Credenziali deboli o di default.
* Mancanza di Multi-Factor Authentication (MFA).
* **Session Fixation:** L'attaccante fissa l'ID di sessione della vittima prima che questa si autentichi, permettendogli di dirottare la sessione dopo il login.

### Insecure Direct Object References (IDOR)
Si verifica quando un'applicazione espone un riferimento diretto a un oggetto (es. un ID nel database come `user_id=1234`) nell'URL o nell'API. Se non ci sono controlli di autorizzazione sul backend, un attaccante può semplicemente cambiare il numero (es. `user_id=1235`) per accedere ai dati di un altro utente.

## 5. Mitigazione e Secure Coding
La sicurezza non è una feature da aggiungere alla fine ("bolt-on"), ma un processo da integrare in tutto il ciclo di vita del software (SDLC).

1.  **Input Validation:** Validare lunghezza, tipo, formato e range di ogni input. Usare una "Allow List" (accettare solo ciò che è noto e buono) invece di una "Block List".
2.  **Output Encoding:** Codificare i dati prima di mostrarli nel browser per prevenire XSS (es. convertire `<` in `&lt;`).
3.  **Principio del Privilegio Minimo:** Il software deve girare con i permessi minimi necessari.
4.  **Testing:**
    * **SAST (Static Application Security Testing):** Analisi del codice sorgente.
    * **DAST (Dynamic Application Security Testing):** Test dell'applicazione in esecuzione (black-box).
    * **Penetration Testing:** Simulazione di attacchi reali.
