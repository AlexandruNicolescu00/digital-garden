# Meccanismi di Presentazione nei Sistemi Distribuiti

## 1. Il Problema dell'Eterogeneità

Uno dei contesti fondamentali dei sistemi distribuiti è la loro intrinseca eterogeneità. I nodi che compongono il sistema possono essere implementati utilizzando **linguaggi di programmazione diversi** (come C, Java, Python), possono essere eseguiti su **piattaforme differenti** (JVM, Python interpreter, Node.js) e su **sistemi operativi diversi** (Windows, Linux, macOS).

Oltre alle differenze software, esistono differenze a livello hardware e di rappresentazione dei dati, come l'**endianness** (Big-endian vs Little-endian). Affinché questi nodi possano comunicare e scambiarsi informazioni in modo fluido, è necessario superare queste barriere tecnologiche. Non è sufficiente che i nodi rispettino gli stessi protocolli di comunicazione (es. TCP/IP); devono anche accordarsi su come i dati vengono rappresentati.

## 2. Il Ruolo dei Meccanismi di Presentazione

I meccanismi di presentazione sono responsabili della rappresentazione dei dati in un **formato comune**, indipendente dalla macchina o dal linguaggio specifico. Questo permette lo scambio di informazioni tra nodi eterogenei.

Il processo fondamentale che abilita questa comunicazione è composto da due fasi:
1.  **Serializzazione (Marshalling):** È il processo di conversione di una struttura dati in memoria (specifica del linguaggio, es. un oggetto Python o una struct C) in un formato "comune" adatto alla trasmissione o all'archiviazione.
2.  **Deserializzazione (Unmarshalling):** È il processo inverso, che ricostruisce la struttura dati originale in memoria partendo dal formato comune ricevuto.

Finché si lavora in un ambiente omogeneo (es. solo Python), spesso la serializzazione è gestita implicitamente (es. tramite `pickle`). Tuttavia, nel mondo reale distribuito, è necessario utilizzare **formati di interscambio dati** standardizzati.

## 3. Formati di Interscambio Dati

Esistono diversi formati popolari, ognuno con le proprie caratteristiche:

* **JSON (JavaScript Object Notation):** È il formato più diffuso per le API web. È testuale, leggero e facile da leggere per gli umani.
* **YAML (YAML Ain't Markup Language):** Spesso usato per file di configurazione, punta sulla leggibilità.
* **XML (eXtensible Markup Language):** Molto verboso e strutturato, storicamente usato nei Web Service (SOAP), ma oggi meno comune per lo scambio dati rapido.
* **TLV (Type-Length-Value):** Un formato binario semplice.
* **Protocol Buffers (Protobuf):** Un formato binario sviluppato da Google, molto efficiente e compatto, usato spesso in gRPC.

### Focus su JSON
Il corso si concentra sull'utilizzo di **JSON**. Le sue caratteristiche principali includono:
* **Struttura:** Basata su coppie chiave-valore (Oggetti) e liste ordinate di valori (Array).
* **Tipi di dati supportati:** Stringhe, Numeri, Booleani (`true`/`false`), `null`, Array (`[]`) e Oggetti (`{}`).
* **Compatibilità:** Praticamente ogni linguaggio di programmazione moderno possiede librerie native o di terze parti per il parsing e la generazione di JSON.

## 4. Esercitazione Pratica: RPC con Autenticazione

L'obiettivo pratico è estendere un sistema RPC (Remote Procedure Call) precedentemente sviluppato per includere un meccanismo di **autenticazione basata su token**.

### Requisiti del Sistema
1.  **Servizio di Autenticazione:** Deve essere presente un meccanismo (es. una funzione `login`) che, date le credenziali corrette, restituisca un **token** (una stringa opaca che rappresenta l'identità dell'utente).
2.  **Gestione del Token:**
    * Il **Client** deve memorizzare questo token dopo il login.
    * Per ogni successiva richiesta "protetta" (come un'operazione di calcolo), il client deve allegare questo token alla richiesta.
3.  **Verifica Lato Server:** Il Server, prima di eseguire l'operazione richiesta, deve estrarre il token dalla richiesta e verificarne la validità.

### Implementazione Tecnica
Per realizzare questo sistema, è necessario modificare la struttura dei messaggi scambiati (serializzati in JSON):
* La classe/struttura `Request` deve essere estesa per includere un campo opzionale di **metadata**.
* Questo campo `metadata` fungerà da contenitore per informazioni di servizio come il token di autenticazione.
* Il `ServerStub` (la parte di codice lato server che riceve la richiesta) dovrà essere modificato per ispezionare i metadata prima di invocare il metodo vero e proprio.

Questa esercitazione simula un flusso reale di sicurezza nelle API moderne, dove l'autenticazione non avviene ad ogni chiamata tramite credenziali, ma tramite il passaggio di un token di sessione o un JWT.
