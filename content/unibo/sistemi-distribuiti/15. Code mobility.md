# C6 – Code Mobility: Spostare il Codice nei Sistemi Distribuiti

## 1. Oltre il Client-Server: Perché la Mobilità?

Il paradigma tradizionale dei sistemi distribuiti è il **Client-Server (CS)**. In questo modello, le risorse e il know-how (il codice) sono statici: il client invia una richiesta, il server esegue un servizio predefinito e restituisce il risultato. Questo approccio, sebbene robusto, presenta limitazioni significative:
* **Traffico di rete:** Spesso è necessario trasferire grandi quantità di dati dal server al client per essere elaborati (Data Shipping).
* **Latenza:** Le continue interazioni (RPC/RMI) introducono ritardi, specialmente su reti lente.
* **Rigidità:** Il server deve avere *a priori* tutte le funzionalità necessarie.

La **Code Mobility** (Mobilità del Codice) ribalta questo paradigma: invece di spostare i dati verso il codice, spostiamo il codice (la computazione) verso i dati o le risorse.

### Vantaggi Generali
1.  **Efficienza:** Si riduce il traffico di rete elaborando i dati localmente dove risiedono.
2.  **Flessibilità:** Si possono aggiungere funzionalità a un server o a un client dinamicamente, senza doverli riavviare o aggiornare manualmente.
3.  **Personalizzazione:** Il comportamento del server può essere adattato alle esigenze specifiche del singolo client.

## 2. Tassonomia della Mobilità del Codice

Per classificare le tecnologie di mobilità, analizziamo le interazioni tra tre entità:
* **Resource (A):** Dati o dispositivi fisici.
* **Computational Component (B):** Il flusso di esecuzione (codice + stato).
* **Execution Environment:** Il nodo che ospita l'esecuzione.

Possiamo distinguere tre paradigmi fondamentali oltre al Client-Server:

### A. Remote Evaluation (REV)
Nel paradigma di *Remote Evaluation*, un componente (solitamente il client) possiede il "know-how" (il codice) ma non le risorse o la potenza di calcolo.
* **Meccanismo:** Il client invia il codice al server. Il server esegue il codice utilizzando le proprie risorse e restituisce il risultato.
* **Esempio:** SQL (invio una query al DB, non scarico l'intera tabella), script server-side inviati dinamicamente.
* **Motto:** "Ho il codice, tu hai le risorse: eseguilo per me".

### B. Code on Demand (COD)
È l'opposto della REV. Il client possiede le risorse ma non sa come elaborarle (gli manca il codice).
* **Meccanismo:** Il client scarica il codice da un repository remoto e lo esegue localmente.
* **Esempio:** Java Applets, JavaScript nel browser (scarico lo script per validare un form o creare un'animazione).
* **Motto:** "Ho le risorse, ma non so come usarle: dammi il codice".

### C. Mobile Agents (MA)
È la forma più avanzata. Qui, un intero componente computazionale (agente) si sposta autonomamente da un nodo all'altro portando con sé il proprio codice e, potenzialmente, il proprio stato.
* **Meccanismo:** L'agente decide di spostarsi ("migrare") per avvicinarsi alle risorse o per interagire con altri agenti.
* **Motto:** "Mi sposto lì per fare il mio lavoro".

## 3. Mobilità Forte vs Mobilità Debole

Quando parliamo di "spostare codice", dobbiamo distinguere *cosa* viene effettivamente trasferito.

### Weak Mobility (Mobilità Debole)
Si trasferisce solo il **codice** (il binario, lo script) e, al massimo, alcuni dati di inizializzazione.
* **Effetto:** Nel nodo di destinazione, il codice viene avviato da zero. Non si conserva lo stato di esecuzione precedente (valore delle variabili locali, punto di esecuzione).
* **Utilizzo:** È il modello più diffuso (es. Java Applets, Servlet) perché facile da implementare.

### Strong Mobility (Mobilità Forte)
Si trasferisce il codice e l'intero **Execution State**.
* **Execution State:** Comprende il valore delle variabili, lo stack delle chiamate e l'Instruction Pointer (program counter).
* **Effetto:** Il processo viene "congelato" su un nodo e "risvegliato" su un altro esattamente nel punto in cui si era interrotto.
* **Difficoltà:** Molto difficile da implementare in ambienti eterogenei perché richiede di salvare e ripristinare lo stato basso livello della macchina (stack, registri).

## 4. Agenti Mobili

Un Agente Mobile è un programma autonomo che può migrare tra nodi di una rete eterogenea.
Non è solo codice che si sposta (come in REV o COD), ma un'entità attiva che decide *dove* andare e *cosa* fare.

### Perché usare gli Agenti Mobili?
1.  **Riduzione del carico di rete:** Spostando l'elaborazione sui dati (es. analisi di log remoti), si evita di trasferire terabyte di dati grezzi (Code Shipping vs Data Shipping).
2.  **Operazioni disconnesse:** Un dispositivo mobile (es. smartphone) può lanciare un agente nella rete fissa, disconnettersi per risparmiare batteria, e riconnettersi ore dopo solo per ritirare i risultati raccolti dall'agente.
3.  **Interazione Real-Time remota:** Se un'applicazione deve controllare un dispositivo remoto (es. un telescopio o un braccio robotico) e la latenza di rete è alta, inviare un agente *in loco* garantisce tempi di reazione immediati.
4.  **Robustezza:** Se il nodo su cui gira l'agente sta per spegnersi, l'agente può migrare altrove per sopravvivere.

### Le Sfide (Il lato oscuro)
* **Sicurezza:** È il problema principale.
    * *Protezione dell'Host:* Come garantisco che un agente ospite non sia un virus o non consumi tutte le risorse (CPU/RAM)? (Soluzione: Sandbox).
    * *Protezione dell'Agente:* Come garantisco che l'host non spii i dati dell'agente o non alteri il suo codice/risultati? (Molto più difficile da risolvere).
* **Interoperabilità:** Gli agenti devono poter girare su sistemi operativi e hardware diversi (necessità di macchine virtuali o interpreti comuni).

## 5. Migrazione dei Processi

La mobilità non riguarda solo agenti intelligenti, ma anche la migrazione di processi standard a livello di Sistema Operativo. Questo è utile per il **Load Balancing** (spostare processi da nodi carichi a nodi scarichi) o per la manutenzione hardware.

Esistono diverse strategie per migrare un processo attivo (trasferire il suo spazio di indirizzamento):

1.  **Eager (Total) Copy:**
    * Si ferma il processo, si copia *tutta* la memoria sul nodo destinazione, si riavvia.
    * *Pro:* Semplice. *Contro:* Alto tempo di "freezing" (downtime) per processi grandi.

2.  **Pre-Copy (Iterativo):**
    * Mentre il processo continua a girare, si copiano le pagine di memoria.
    * Se alcune pagine vengono modificate (dirty pages) durante la copia, si ricopiano solo quelle.
    * Si ferma il processo solo quando le pagine rimaste da copiare sono poche.
    * *Vantaggio:* Riduce drasticamente il tempo di fermo (usato nella Live Migration delle Virtual Machines).

3.  **Lazy (On-Demand) Copy:**
    * Si copia solo lo stato essenziale (registri) e si avvia subito il processo a destinazione.
    * Le pagine di memoria vengono recuperate dal vecchio nodo solo quando il processo tenta di accedervi (Page Fault).
    * *Vantaggio:* Avvio immediato. *Svantaggio:* L'esecuzione iniziale è lenta a causa dei continui trasferimenti di memoria.

### Migrazione delle Virtual Machines (VM)
Oggi, la forma più comune di mobilità forte è la **Live Migration** delle macchine virtuali. Invece di migrare un singolo processo (complesso a causa delle dipendenze con l'OS, file aperti, socket), si migra l'intero Sistema Operativo "virtualizzato". Questo isola le dipendenze e rende la migrazione trasparente alle applicazioni.
